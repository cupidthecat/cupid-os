# ADR 0296: Support mixed floating compound assignments

## Status

Accepted on 2026-08-15.

## Context

Hosted CupidC already applied the usual arithmetic conversions when a runtime
arithmetic expression mixed a represented integer with `float`, `double`, or
`long double`. Its i386 emitter also had the target instructions needed to
convert the floating result back to each represented integer width.

Compound assignment stopped before those paths. A floating lvalue rejected an
integer right operand, and an integer lvalue rejected a floating right operand.
The same boundary blocked `long double` compound assignment. This made ordinary
expressions such as `sample += count` and `count /= scale` fail even though the
corresponding binary operation and store conversion were already represented.

Changing source operands or narrowing them first would change C semantics. A
compound assignment must evaluate its left designator once, perform the usual
arithmetic conversions, convert the result back to the left type, store it, and
produce the stored value.

## Decision

Accept `+=`, `-=`, `*=`, and `/=` when exactly one operand is a represented
integer or compatible enum and the other is `float`, `double`, or `long
double`. Either operand may be the lvalue. The lvalue must remain non-atomic.

The frontend applies integer promotion to an integer right operand and records
the floating common type. A floating right operand supplies that common type
for an integer lvalue. If either floating operand is `long double`, the
computation uses `long double`; otherwise `double` outranks `float`.

Linear IR duplicates the destination address, loads the left value, converts
it to the floating computation type, evaluates the right operand, performs the
selected arithmetic operation, and applies assignment conversion back to the
declared left type. `STORE_VALUE` writes once and leaves the stored value as the
expression result.

Represented signed and unsigned integer bit fields use the same order. Their
record designator is evaluated once, the extracted and promoted lane converts
to the floating computation type, and the result converts back before the
existing width-aware bit-field store.

Linear IR and object validation admit floating-to-integer conversion for every
represented integer width when the conversion kind is `ASSIGNMENT`. This is
the conversion generated by compound assignment. The existing explicit-cast
and plain hosted assignment boundaries do not change.

The emitter reuses its existing SSE and x87 conversion paths. Wide signed and
unsigned destinations use truncate-mode `FISTP` and the established unsigned
64-bit split. Integer input uses SSE through four bytes or x87 `FILD` at eight
bytes. Long-double values retain twelve-byte snapshots and 80-bit loads and
stores. No runtime helper, host floating operation, ABI rule, relocation, or
object format is added to production code.

Atomic floating lvalues keep the focused
`atomic floating compound assignments are not supported` diagnostic. An
atomic operand in an otherwise mixed expression reports
`atomic mixed floating compound assignments are not supported`. The same job
can parse or emit a valid unit after either failure.

boundary. The object contract then exposed two missing operations in its

truncate-mode `FISTP`. Those executor operations were added so the public
object result could be checked at runtime; they do not alter production
emission.

## Rejected alternatives

Rewriting mixed compounds as separate source assignments was rejected because
the left designator could run twice.

Requiring an explicit cast on the right operand was rejected because compound
assignment uses the usual arithmetic conversions without one.

Converting an integer lvalue before the operation and leaving the floating
result unstored was rejected because the assignment conversion and expression
result are part of C semantics.

Treating a bit field as an addressable scalar was rejected because a C bit
field has no address and neighboring bits must survive the store.

Using host floating conversion in the emitter was rejected. Existing target
SSE and x87 paths already own the result and preserve the i386 contract.

## Consequences

Source-head hosted CupidC now supports mixed arithmetic compound assignment
across its represented non-atomic scalar and integer bit-field types. The
frontend, Linear IR, and deterministic object emitter agree on the computation
type, conversion order, single evaluation, store width, and expression result.

The checked execution seed predates this change. No active OS translation
requires the new expression shape, so this decision moves no production owner
and changes no normal OS object, ABI, build dependency, or source suffix. A
later seed promotion must carry the compiler and contracts before the checked
toolchain can claim the capability.

Atomic mixed compound assignment, atomic floating access, `long double`
increment and decrement, general explicit floating-to-wide casts, and plain
hosted floating-to-wide assignment remain open. `TempleOS/` remains untouched
reference material.
